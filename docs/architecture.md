# Architecture

This page describes how the renderer is built. The decisions behind it are in
[decision records](decisions/). Read [Concepts](concepts.md) first for the vocabulary, and
[Styles and preferences](style-templates.md) for configuration.

---

## The pipeline

```
 source .lgd
      │  normalize_source(): strip BOM, unify line endings
      ▼
 ┌─────────────────────────┐
 │ 2. Assemble (answers)   │  only with an answers set: legaldown-validator's Template and Form
 └───────────┬─────────────┘  turn the template into its assembled document, which the rest renders
             ▼
 ┌─────────────────────────┐
 │ 1. Parse & validate     │  legaldown-validator: Document, ValidationResult (Core diagnostics;
 └───────────┬─────────────┘  its index: identifiers, markers, party/side/definition/attachment lookups)
             ▼
 ┌─────────────────────────┐
 │ 3. Build     build.py   │  source + validator → render tree (source inlines)
 └───────────┬─────────────┘
             ▼                style template (style/) ──┐
 ┌─────────────────────────┐                            │
 │ 4. Resolve   resolve/   │ ◄──────────────────────────┘  numbers, labels, anchors, display text,
 └───────────┬─────────────┘                               failure markers + Rendering diagnostics
             ▼
 ┌─────────────────────────┐
 │ 5. Write     writers/   │  html │ text │ docx   (pdf later)
 └───────────┬─────────────┘
             ▼
 RenderResult(output, diagnostics, format, tree, style, binary)
```

Stage 2, **assembly** with an answers set (§15.7), runs only when the job has answers, before
the document is parsed for rendering. A template rendered with answers is assembled first and the
assembled document rendered; without answers, it renders as its **template view** (§15.8).
Assembly is the core package's (`legaldown.parse_template(source).form(answers).assemble()`),
exact to the byte as §15.7.2 requires; the renderer only decides when to refuse:

- the template has Errors: §15.7.2 defines assembly only for a template without them
- the answers do (`answer-invalid`, `answer-missing`)
- the template needs other files (include fragments, LegalDown attachment files, translations),
  which the renderer does not read below the Full level (§17.6)

A refusal raises `RenderRefused` with the findings. Assembly Warnings, such as `answer-unknown`,
are reported with the rest. Blanks left unanswered stay, and render as blanks: the result is a
draft (§15.1), which `--final` reports.

`api.render()` runs the pipeline. Each stage returns frozen values. Only stage 4 reads the style's
semantic settings, and only stage 5 knows about file formats.

### 1. Parse and validate

`legaldown.parse` and `legaldown.validate` provide:

- the **metadata**: title, sides and parties, attachments, questions, language
- the **section identifiers** exactly as the validator resolved them: explicit `{#id}`, or
  generated by §5.3 with §5.5 collision handling. These come from `result.index.sections`,
  so the renderer can never compute a different anchor than the one the validator checked
- **lookups** for definitions, parties, sides, and attachments, already reduced to display names
  (§3.6)
- the **Core diagnostics**, each with a stable rule id

A document that cannot be read at all, such as one whose frontmatter is not valid YAML,
raises `DocumentError`. Every other problem renders.

### 3. Build the render tree (`build.py`)

There is one parser: the validator's ([ADR 0007](decisions/0007-one-parser-validator-model.md)).
The builder walks the validator's `Document` and turns each block into render-tree blocks. It
never decides a structural or LegalDown question itself:

| Question | Answered by |
|---|---|
| Sections, headings, identifiers | `Document.sections`, `result.index.sections` |
| Blocks: paragraphs, lists and items, quotes, tables, code, rules | `Document` blocks. List items hold blocks (nested lists, code, quotes, tables), a quote's content is the validator's `quote_blocks()`, and a code block's is `code_content()` |
| Where a marker (`{#id when=…}`) is placed, and what it means | `result.index.placed_markers`: each marker's block, field, offset, identifier, and condition |
| Whether the document is a template | `result.index.is_template` |
| Whether a quote is a drafting note, and its content | The validator's `is_drafting_note()` and `drafting_note_blocks()` |
| Which list item a marker belongs to | `PlacedMarker.item`: the item's number among the list's items, in pre-order |
| A lifted definition, `{{ref:}}` or `{{term:}}` block's source | The validator's `render_block()` |
| The line of a heading, a top-level block or a list item (§16.9) | `Document.line_of()` |

These are all the validator's public API: the model and the result from `legaldown`, and, for
assembly, `parse_template` (`Template.form().assemble()`), `AssemblyError`, and the answers
reader `load_answers`, also from `legaldown`; the reading of source text from `legaldown.syntax`;
and the language's constants and rules from `legaldown.grammar`.

Within one block's text, **markdown-it-py parses inline Markdown only**: emphasis, links, code
spans, inline HTML. Directives are protected first by **sentinels**. Every directive, and every
`"Term" {{def:}}` span, is replaced with a private-use token, `\ue000<nonce>:<n>\ue001`, so
Markdown cannot reinterpret directive syntax, such as an underscore in an identifier. The nonce is
random for each build, so no text in a document, whether written literally, as an entity, or
percent-encoded, can pass for a sentinel. Emphasis that wraps only a defined term is dropped with
it, because the style decides how defined terms look (§7.2). A `{{def:}}` becomes a sentinel
that renders nothing. Every sentinel is wrapped in a punctuation character (U+2E31, Unicode
category Po, which markdown-it's `isPunctChar` accepts) on both sides, as the `{{` and `}}` it
replaces are punctuation, so that CommonMark's emphasis flanking rules see the same neighbours as
in the source: `_text_{{ref: a}}` closes its emphasis. A defined term in a link title or alt text shows its term but is not the
definition's anchor.

An HTML block in the model (`kind="html"`), a comment block included, renders nothing (§8.6). A
comment that starts a line is such a block, and it ends at the line holding `-->`, so text after
the `-->` on that line is dropped with it (CONFORMANCE.md, "Text after a comment").
Within a block's text, inline comments and tags are dropped; where one stood between two spaces,
one space stays, and before a line break none does. A list item whose blocks are all comments,
and a quote that holds only comments, are dropped (with a list left empty), after the whole list
is traversed so that the validator's item numbers stay aligned with the markers it placed. The
validator reports raw HTML other than comments (`raw-html`, §8.7). A heading
in a list item or a quote (`kind="heading"`) is not a section (§4.1) and shows as a bold line.

The builder never works around the validator's model. Where the model loses or misreads
something, the output follows the model, and the gap is listed in `CONFORMANCE.md` and filed on
the validator:
- link reference definitions (`[label]: url`) render as paragraphs

Guessing at lost structure was tried, and it traded each gap for new bugs.

### 4. Resolve (`resolve/`)

`Resolver.run()` works in three steps:

1. **Survey.** It finds which placeholder ids are used with conflicting types (§10.7). Which
   definitions exist (`result.index.definition_lookup`) and whether the document is a template
   (`result.index.is_template`) are the validator's, so there is nothing to collect for them.
2. **Structure.** Section numbers are the validator's own (`result.index.sections`), so a
   rendered number always matches the validator's: **alternatives** share a number (§15.8), and
   a skipped heading level counts as 1. The style only formats them, the n-th part of a number
   with the n-th level format. For paragraphs and list items, **alternatives** follow the
   validator's rule, applied the same way: an alternative directly follows its
   sibling among the units numbered together (a list or table between two top-level paragraphs does
   not separate them), has the same identifier and a valid condition, and its full presence (its own condition
   and every enclosing one) excludes that of every unit already holding the number (§15.4, the
   validator's `exclusive()`). It then labels
   list items by depth and top-level paragraphs, and allocates output anchors. Every anchor
   target is registered with its **designation**: "4.2", "4.2(b)(ii)", or "Termination (a)"
   under the `none` scheme, where it is worked out from the headings (see below).
3. **Inlines.** It replaces every source inline with a resolved one:

| Directive | Resolves to | Failure markers |
|---|---|---|
| `{{ref:}}` | `CrossRef(designation, anchor, target_unit, section_unit)` (§13.3). A ref to an unnumbered item or paragraph falls back to its section's designation, with `ref-not-enumerated` | `[BROKEN REF: id]` |
| `{{term:}}` | `TermRef(label or the definition's rendered term text, def anchor)` (§7.3, §13.4); the text is the first definition's term resolved as at the definition, worked out on first use by `Resolver._term_text` (`_survey` only records which definition is first) | `[UNDEFINED: id]` |
| `"Term" {{def:}}` | `DefinedTerm` without quotation marks, anchored at `def:<id>` (§7.2) | n/a |
| `{{date:}}` `{{money:}}` `{{duration:}}` | `Value`, formatted for the locale by Babel (ADR 0005): amounts and durations keep every written digit (a fraction beyond Python's 4300-digit limit takes its plural form from its first 30 digits), and a duration without a pattern in the locale falls back to another length, the language alone, then English with `render-locale-fallback` | `[INVALID DATE: …]`, `[INVALID AMOUNT: …]`, `[UNKNOWN CURRENCY: …]`, `[INVALID DURATION: …]`, `[INVALID DURATION UNIT: …]` |
| `{{party:}}` `{{side:}}` | `Value(label or display name)` (§3.6) | `[INVALID PARTY: …]`, `[UNKNOWN PARTY: …]`, and the side forms |
| `{{field:}}` | `Value(raw value)` | `[INVALID FIELD: …]` |
| `{{placeholder:}}` | `Blank`, with the question's prompt if the style asks for it | `[INVALID PLACEHOLDER: …]`, `[UNKNOWN CURRENCY: …]`, `[INVALID DURATION UNIT: …]` |
| `{{attach:}}` | `Value(label or title)`, linked to the attachment placeholder or file (§6.4) | `[UNKNOWN ATTACHMENT: id]` |
| `{{choose:}}` | `Choice(all phrases)`, shown as `[a / b]` (§15.8) | `[INVALID CHOICE: q]` |
| `{{include:}}` | Not processed at this level (§17.5), with `render-not-processed` | `[NOT PROCESSED: include path]` |
| unknown name | Never printed verbatim (§11.5) | `[UNKNOWN DIRECTIVE: name]` |

A `label` never hides a failure marker (§11.5). Frontmatter strings go through the same resolver,
so placeholders in frontmatter render as blanks (§3.10).

The resolver also builds the **title block** (effective date, sides and parties; a party is named
there by `legal_name`, as an identification block, where `{{party:}}` in the text shows its
`label`, §3.6), **attachment
placeholders** (§13.8; files are not read at this level), and **signature blocks** (§2.2, always
with `legal_name`, per §3.6).

**Anchors.** Section, item, paragraph, and attachment anchors use their identifiers. Definition
anchors are `def:<id>`. Identifiers cannot contain `:`, so the two can never collide in HTML's
single id space (§5.6). When alternatives share an identifier, only the first keeps the anchor,
so ids stay unique. A definition's anchor is given out in one place, when its defined term is
resolved. Terms in titles or alt text get none. After everything is resolved, one pass drops the
link of any `{{term:}}` whose definition got no anchor, so term links always have a target.

Headings are numbered with their level clamped to 1–5, as the validator numbers them.

**The numbering structure in the tree.** The resolver is the only place the rules of §13 live, and
a writer that builds numbering of its own (DOCX does) must not work them out again. So the tree
carries the structure behind every number, in terms that name no output format:

| Where | Field | Holds |
|---|---|---|
| `RenderTree.version`, `RenderTree.effective_date` | `str` | The frontmatter's version and effective date as plain text, exactly as the title block shows them (directives resolved, a valid date formatted by the style for the locale), **whether or not** `title_block` shows them: a running header or footer uses them (`{version}`, `{date}`). Empty when absent |
| `RenderTree.formats` | `NumberingFormats` | The formats the labels were made with, after the style is resolved: `scheme`; `headings`, one `LevelFormat` (counter, `label` and `ref` templates) per heading level (empty under `none`); `enumerated`, the formats by list depth (cycling); `renumber`, the one format of ordered lists (None under `enumeration.ordered: enumerate`); `paragraphs` (None unless numbered); `reference`, `references.format` |
| `Section`, `ListItem`, `Paragraph` | `unit` | An id, unique in the document and equal on every render: `s<k>` for the k-th section, `u<k>` for the k-th item or top-level paragraph of a section in document order, the preamble first. Not the anchor. Every section, every item (in a quote too) and every top-level paragraph of a section has one, numbered or not, since an unnumbered one can still be the target of a reference; a paragraph inside an item, or in the preamble, is not a unit (None) |
| same | `number` | The unit's own counter value (the last part of "2.1" is 1; the item's position in its list; the paragraph's in its section). None when the unit is not numbered: any section under `none`, an item of a list that is not enumerated, a paragraph when the style does not number them |
| same | `parent_unit` | The unit its designation is built on. For a section, the nearest section above it with fewer number parts (a skipped heading level counts as 1 and is no unit: "1.2.1.1" under "1.2" has a gap of one level, which `level` shows); for an item of a list not nested in an item, and for a paragraph, its section (None in the preamble); for a nested item, the item. A list in a quote or drafting note, even inside an item, is built on the section, as its designation is; to see where a list nests, follow `parent_unit` (an item or a section), never `depth` |
| same | `shares_number_with` | For a later alternative that shares its number (§15.8, §15.4), the unit of the **first**; None otherwise, and always None on an unnumbered unit. Every alternative has a unit of its own. Sections share by number, as the validator numbers them: the subsections of a later alternative section repeat the numbers of the earlier one's ("1.1" again), and each repeat shares the number of the first section that had it |
| `List` | `family` | `renumber` (ordered, counted 1., 2., … whatever the source says), `enumerated` (counted in the format of the nesting depth) or `bullet` (no numbers; `enumerated` is False) |
| `List` | `depth`, `format`, `start` | The nesting depth the format was chosen at (a list in a quote in an item is one deeper), which selects the format and nothing else; the `LevelFormat` itself, so the entry of `formats` is never selected again (None for `bullet`); and `start`, the number of the first item (`items[0].number`). A list is not always counted from 1: lists nested directly in one item share a counter per way of writing a designation (counter style and `ref`), so a second list after a paragraph, or a renumbered list beside an enumerated one with the same designations, continues the first's numbers (a, b, then c) and no designation repeats; top-level lists and lists in quotes start at 1. A list has no id of its own: name it by `items[0].unit` |
| `CrossRef` | `target_unit`, `section_unit` | The unit the identifier is on, and the section that qualifies the designation (for a section target, itself). With alternatives sharing the identifier, `target_unit` is the first, as the anchor is. For an unnumbered item or paragraph the unit is still the target and `text` is the section's designation. Under `none` both are set as usual and the section's `number` is None. A reference that does not resolve is a `FailureMarker`, and so is a `{{ref:}}` to an attachment id (§5.6); an attachment is reached with `{{attach:}}`, a `Value` whose `href` is `#` and the `AttachmentPart.anchor`. Both are None for a copy that no longer links (`unlinked`, as in the table of contents) |

A designation is the parent's designation followed by the unit's `ref` template filled in
(`{n}` the unit's number in its counter style, `{section}` the designation of the section, which a
preamble item has none of; under `none` the heading text stands for the section's designation and a
space goes before the piece), and a label is the unit's `label` template filled in with the same and
`{path}`, the designation up to the unit. `tests/test_numbering_structure.py` writes every label,
designation and reference text again from these fields alone, for each built-in style and the
specification's corpus, so the structure is known to be enough.

Unit ids come out the same in the second numbering pass of the `none` scheme (below): they follow
document order, and the counter starts again with each pass.

**Designations under the `none` scheme (§13.3).** A section's designation is its heading as
rendered, as plain text with white space collapsed: the `{{ref:}}`s and `{{term:}}`s in it are
resolved (a reference shows `references.format` applied to its target's designation, so
`# About {{ref: ov}}` is "About Overview"), a broken reference shows its marker. An item's or
paragraph's designation is its section's with the item pieces after it ("Termination (a)"). A
heading can refer to a heading, item or paragraph anywhere, so designations are worked out in
four steps. They run only when the scheme is `none` and a section heading, or the text of a term a
heading uses (directly or through other terms), holds a `{{ref:}}`; for a term whose definition is
not in the body, the validator's own text of it is searched for `{{`. Otherwise the first step's text
is final and nothing more is done. (A value of the frontmatter that a heading shows, with
`{{party:}}` or `{{attach:}}`, is not searched: a `{{ref:}}` in it is not designated through.)

1. Every section, item and paragraph is numbered on a **provisional** designation: the heading's
   text-only reading (`Resolver._title_text`, which leaves references out). Each target records
   its section and the pieces after it (`_Target.section_index`, `parts`).
2. `Resolver._designate` works out every section's designation once, by a depth-first walk in
   document order that memoises: a reference reads the designation of its target (an item's or
   paragraph's is its pieces put together again on its section's, `_compose`), which is worked out
   on the spot if it is not known yet. The walk reads headings with `_title_text`, so it gives out
   no anchor, and reports nothing itself (what it resolves is read again in its place, where a
   diagnostic about a heading is made once); its term texts have a cache of their own, apart from the
   later pass's.
3. Where any designation differs from the provisional one, the numbering of step 1 is done again on the
   final designations (labels, designations, `render-ref-ambiguous` slots). Anchors are given out
   in the same order and so come out the same.
4. The inlines are resolved as for every scheme, now with every designation known.

A heading that reads itself again (directly, through other headings or terms, or through its own
item) reads as its provisional text where the circle closes, with the Warning
`render-designation-cycle`. A heading read from the text of a term it uses is such a circle, and what
it reads there is not kept (it is worked out again where the term is not open). A walk through more
than 32 headings, a designation longer than 1,000 characters once its references are resolved (a
chain of headings that each cite the next twice would ask for 2^n), or inline levels nested past 60
(counted from where the outermost open term began, or from the heading where the walk started: so a
heading with 59 or more nested emphasis levels that holds a reference can reach it after one hop)
also give the heading's provisional text, with `render-designation-limit` (so does a term the walk
cut by the term limits). A ring of more than 32 headings is therefore reported as a limit, not as a
cycle. A `{{ref:}}` shows at most the first 1,000 characters of a heading (the item or paragraph
piece after it is kept), and `render-designation-limit` says so for that heading. So a heading in a
cycle or past a cap, or one whose terms reach into one, may read differently from the designation
references show; the Warning says so. Every other heading reads exactly as its designation.

### The DOCX planner (`resolve/docx_plan.py`)

The DOCX writer contains no numbering rules either (ADR 0003, [ADR 0008](decisions/0008-docx-word-native.md)).
Between the resolved tree and that writer sits a pure function, `plan_docx(tree, *, file=None) -> (DocxPlan,
diagnostics)`, which maps the numbering structure above to what Word needs: the abstractNums and nums, for every
section, list item and numbered paragraph the `(numId, ilvl)` its paragraph takes, the bookmark of every anchor, the
fields of every cross-reference, and the entries of the table of contents. It reads only `tree.formats` and the
units' `number`, `parent_unit` and `List.family`/`depth`/`format` (`numbering.formats_of(style)` builds `formats` for the
resolver and for the style check), and checks every placement against the number the resolver gave the unit by
simulating Word's counters (`resolve/docx_numbering.py`), so that what Word draws is what the resolver numbered, or a
diagnostic says why not. It is a planning step, not a stage of the pipeline: `render(format="docx")` calls it after
resolution, passes the plan to the writer, and adds its diagnostics (named with the document's file, each finding once,
ordered by line with the renderer's own) to the result's. The style check, `docx_style_errors(style)`, runs earlier still, in
`style/docx.py:docx_settings`, before rendering (ADR 0006).

**Word's list semantics**, stated once (the planner and its diagnostics rely on them):

- Counters belong to the abstractNum and are shared by every `w:num` of it. A num with a `startOverride` restarts
  the named level at the first use of that num, and the levels above keep their values: this is Word's own
  "Restart at 1". A level that nothing numbered before a deeper one is read by Word as 0 (the renderer counts a
  skipped heading level as 1, and so does LibreOffice).
- A paragraph restarts every deeper level. A paragraph with `numId 0` counts nothing and restarts nothing.
- A list nested in an item of the same kind goes on a deeper level of its parent's num, so it restarts by
  structure when a parent item is added. A list of another kind, a list in a quote, and a list Word would continue
  where the resolver restarts have a num of their own: it restarts at 1 by a fixed setting (an item added above it
  in Word does not restart it). A list that the resolver continues (its first item is 3) but Word cannot continue
  starts at that number by a fixed setting, which does not follow items added or removed before it.
- A bullet counts nothing: one num serves every bullet list.
- Paragraph numbering has one num per section, and a section added in Word does not restart it by itself.
- Word has no way to give two paragraphs the same number on one level, except `numId 0` and a field: a paragraph with
  a counter always counts. A unit that must read the number of the one before it (an alternative, §15.8) is a
  `numId 0` paragraph that starts with a `REF \n` field of that unit.
- `REF <bookmark> \n` returns the paragraph's level text with its counters, minus trailing periods.

**What is planned.** Heading numbering (one multilevel abstractNum linked to the heading styles, the label templates
turned into `lvlText`, the counters into `numFmt`), list families (enumerated, renumbered, bullets) with their nesting
and restarts, depth beyond Word's nine levels (clamped to level 9 in that level's format), and numbered paragraphs.
A level of a list shows only counters of its own list, which settles where the rest of the planner puts things:

- **Labels that need the section** (`{section}`, or the `{path}` of an item or paragraph in a section: the continental
  style's `5.1`, the default style's numbered paragraphs `1.1`). Only the heading list can show the counters of a
  section, so a unit whose label needs them goes on the heading abstractNum at the level after its section's
  (`%1.%2` after a level-1 section), where the level reads exactly as the label does (`candidate` equals the heading
  level; the first top-level list of the section gets one num with a `startOverride`, as every top-level list does).
  Such an item is no heading: it has no heading style, no outline level and no entry in the table of contents, and
  carries an indent of its own (`UnitPlan.ind`; a heading level's `w:ind` serves the heading). A list nested directly
  in an item that is on the heading list goes on the heading abstractNum's **reserved levels**, level `4 + d` for
  nesting depth `d` of 1 to 4, defined on first use with the label's text without the section (`%6)`, `%7)`), on the
  same num as its parent with no override: it restarts by structure under every new item and sibling lists go on
  counting, as in any other list. A level may be shared by units whose definitions are equal and is kept for the first
  that needs it otherwise; the level after the fifth heading level is kept for a level-5 section's units when the
  document has one, and a nested list then falls back. The built-in continental style uses levels 6 and 7 (`a)`, `i)`); its third level of nesting under a clause shows the section's number and falls back (static, reported). What does not fit (an outline or mixed scheme, where the
  level after the section's reads otherwise; the `none` scheme, where the section's number is its text; a nested
  item whose label shows the section; items in a quote; ordered and bullet lists nested in such an item; depth past
  4) keeps the family's own abstractNum with the label written without the section and reported
  (`render-docx-section-label`); the references still cover it.
- **Alternatives that share a number** (§15.8). A unit that shares its number with the one before it and that Word
  would number differently (the live number would continue) is a `numId 0` paragraph with its own indent that starts
  with a `REF \n \h` field of the unit that holds the number now, then the label's text beyond what the field returns
  (the period) and a tab or space (`UnitPlan.alt`, `ind`); that unit gets a bookmark, a `{{ref:}}` to the shared
  identifier is a reference to the first alternative, and the table of contents shows the shared number for the later
  one. The units under a later alternative restart in a num of their own with a `startOverride` (the sections after a
  later alternative section until one of its level or above; a list nested in a later alternative item), because the
  alternative counts nothing and Word would go on counting from the holder's children. A later alternative whose live
  number is already right (the children of a later alternative section repeat the numbers of the first's) is numbered
  live. Designations below an alternative are made of the holder's counters. This is live for edits elsewhere but not
  for the first alternative: deleting it in Word breaks every later alternative and every reference to the shared
  identifier, and Enter at the start or end of a later alternative gives an unnumbered paragraph, so the render reports
  one information per document (`render-docx-alternative`) and a final document is made by rendering with the
  condition values.
- **Resynchronising.** A numbered unit that Word would number differently from the resolver for want of a place where it
  can count by structure (it goes on a counter that other units of the same abstractNum have used) is put on a num with
  a `startOverride` at its number, and the units after it go on counting on the original. This is a fixed value: a
  restarted sub-heading keeps it when clauses or headings are inserted before it, and the headings after it read
  higher if it is deleted; a restarted clause or paragraph does not follow what is inserted or deleted before it. It repairs a sub-heading after the
  items and paragraphs of its section on the heading list (`1.1` for the sub-heading and for the first item share a
  counter in Word and a designation in every output format: `render-docx-shared-counter` says so), a list that
  resumes a sibling's count after another list in the same item, and a list past level 9.

A list nested in an item that has an indent of its own (`UnitPlan.ind`) is indented one step in from it, on whatever
list it is. A label that shows a counter of a unit outside the unit's own chain (a quote's list inside an item of the preamble,
whose label starts from the item; a list nested in another kind of list) is written with the counters Word has there
and reported. Nothing is left to be shown by Word differently without a diagnostic.

**Cross-references: the designation cover** (`resolve/docx_cover.py`, §6.3, §13.3). The renderer's text of a
`{{ref:}}` is the designation of the target (`1.1.1`, `I.A.1.a(i)`, `1(b)(ii)`) inside `references.format`; the planner
writes the designation of every unit as a *token string* (a counter with the unit that holds it, literal text, or a
heading's text under the `none` scheme) in the same pass that numbers it, ported one to one from the resolver's `fill`
and `extend`. In Word every part of it that Word can compute must be a field, and nothing Word can compute may be
literal text, so the plan covers the designation by `REF <bookmark> \n \h` fields and the delimiters between them.
A field returns the full level text of the bookmarked paragraph with its counters, minus trailing periods (what the
simulator gives as `Step.word_ref`), and fits where its counters belong to the same units as the designation's: a
`{path}` label (`1.1.1`) is covered by one field on the target, a `{n}` label (`I.A.1`) by one field per level with
literal delimiters between (`I` `.` `A` `.` `1`), a nested item (`(b)(ii)`) by one field per level, an ordered
list in a section by `REF section` + `(` + `REF item` + `)`. Literal text may stand only for delimiters, never for a
counter. The cover with the fewest fields wins, then the fewest using `\t`, then the fewest literal characters;
the text of `references.format` is literal around it, and with two `{designation}` the same cover is written twice.
`\t` (Word's switch that suppresses the words around a counter; LibreOffice ignores it) is used only where it leaves
the bare counter (`Article I` gives `I`, `§ 3` gives `3`), never where the field's text holds a delimiter
(`(a)`, `a)`, `1.2`, and also a period: `No. 1`, so `No. {n}` has no `\t` form; this is conservative, because
what Word does with a delimiter is not known, and is on the manual Word checklist). Each field's cached result is
**Word's** value (the simulator's), and `cached_lo` what LibreOffice shows. A unit that a field points at has a
bookmark (its anchor's, or a hidden one); a reference to an item or paragraph the style does not number is the
designation of its section (`ref-not-enumerated`), covered as one. Under the `none` scheme a heading is a field for the
bookmarked text (`REF bookmark \h`) and the item's pieces follow after a space; what the field returns is what the
heading's runs show (`_shown`), which can differ from the renderer's designation by white space, and then the
reference is reported. A `RefPlan` is made once per target, keyed by `CrossRef.target_unit`; `exact` says that the
cached results read as the renderer's text. **When no cover exists** (a heading level skipped before the target under
a `{n}`-style scheme, text around a counter that `\t` cannot drop) the reference is the renderer's text with no field
(`RefPlan.fixed`): it reads right when the file is opened and does not follow edits, and `render-docx-reference` says
so (one finding for the references that fail alike, naming the first and how many more). Nothing that Word could
compute is written as literal text otherwise.

**Bookmarks** (`resolve/docx_bookmarks.py`). The planner names bookmarks and the writer gives them ids. Every anchor of
the tree has one, referenced or not: `ld_<anchor>` for a section, list item or paragraph, `lddef_<id>` for a
defined term, `ldatt_<id>` for an attachment, `_LdAttachments` for the attachments heading, with `-` and `:` written
as `_`. A name is used only if it is valid, at most 40 characters, nothing but dashes was changed, and it is unique
ignoring case (Word compares names so); otherwise, and for a unit a field needs that has no anchor, it is hidden:
`_Ld<k>`, counted in document order. The table of contents uses `_Toc<nine digits>` from 100000001. The writer wraps
the paragraph's title or first paragraph in `UnitPlan.bookmarks`, then `toc_bookmark`; a term reference and an
internal link point at `plan.anchors`. **A bookmark holds text only when a field returns that text** (`REF \h`, a
heading under the `none` scheme): every other bookmark is a point at the start of the paragraph
(`UnitPlan.collapsed`), because `REF \n` needs only the paragraph, and a field inside the bookmark it points at is
a self-reference that Word cannot show and LibreOffice expands without end. Under the `none` scheme a heading whose
title holds a reference that leads back to the heading, directly or through the titles of other headings, would have
exactly that; the plan lists those references (`UnitPlan.literal_refs`, by target) and the writer writes them as
their text, and `render-docx-reference-cycle` says so, naming the heading's line (the renderer already warns with
`render-designation-cycle`). The headings are the nodes of a graph, an edge for each heading whose text a field in
another's title returns, and a reference in a title is a cycle exactly when such a field's heading is in the title's
own strongly connected component (found once, iteratively: linear in the headings and references). The text a
heading field returns is worked out from the runs, in the order the components complete: a reference in the title is
the text of the fields it is written as (the cached results of other headings' fields), or its own text where it is
written as text.

**The table of contents.** `ContentsEntry.unit` (the section's unit; None for the attachments heading and an
attachment) keys each entry of `tree.contents` to its section. `plan.toc` lists the entries in order with
the number Word draws for the heading (`UnitPlan.label`, so a style's `Article I` is the number Word shows, not
a rendering of the renderer's), the separator the level has (`suff`: tab or space; none for an unnumbered entry), the
title, the condition label, the `_Toc` bookmark (also `UnitPlan.toc_bookmark`) and an empty cached page number. The
complex `TOC` field that uses them is written with the title block.

**Diagnostics** (all `render-docx-*`, with the line of the unit or of the reference, once per finding): `section-label`,
`list-depth`, `letter-overflow` (Word repeats letters after 26, the renderer counts on: `aa`, `ab`), `roman-overflow`
(4000 and beyond), `shared-counter` (a unit that goes on a counter of its abstractNum that others have used, so that it is restarted at
its number, a fixed value that will not follow edits before it: a sub-heading that shares a designation with the
items of its section, a list that goes on from another, a list whose level another used in between), `number-mismatch` (any
other difference: the first unit of a run that Word counts off by the same amount, with how many follow; it is the
catch-all of the planner and does not occur outside documents that skip a heading level), `reference` (a
cross-reference that cannot be built from fields, because a heading level is skipped before the target with a
`{n}`-style scheme, or Word draws text around a counter that `\t` cannot drop (`({n})`, `{n}:`, `No. {n}`): it is
written as fixed text; or one that reads differently in Word for a reason that no diagnostic of a unit already
gives; references that fail alike are one finding), `reference-cycle` (a heading's title holds a reference that
leads back to it: written as text), and, as information, `alternative` (alternatives share a number as fields of the first, which deleting in Word breaks), `static-restart` (a list that restarts at 1 by a
fixed setting: nested in a list of another kind, in an item whose number is on the heading list but which the list
cannot ride, or in an alternative that shares a number) and `reference-word-only` (a cover relies on `\t`, which LibreOffice ignores, once per document). A
heading level that is skipped is the Core Error `heading-skip`; the plan only notes it on the unit.

## Dependencies

| Dependency | Why |
|---|---|
| `legaldown-validator>=0.4.0,<0.5` | The only LegalDown parser; Core validation |
| `markdown-it-py` | Inline Markdown inside one block's text (ADR 0007) |
| `babel` | CLDR locale data (ADR 0005) |
| `pyyaml` | Style templates |

All of them are pure Python. The DOCX writer needs nothing more (it writes OOXML itself, ADR 0008); the PDF writer will bring its dependency in as an extra. `lxml` is a test dependency only (`dev` extra), for validating DOCX parts against the OOXML schemas.

The renderer uses only the validator's public API: `legaldown`, and the tooling modules
`legaldown.syntax` and `legaldown.grammar` (roadmap item U3, done in validator 0.4.0). Before 1.0
a minor release of the validator may change that API, so the dependency is pinned to one minor
version, and the tests fail on any of its deprecation warnings, since the next minor release
removes what is deprecated. The validator raises every one of them as a
`legaldown.LegaldownDeprecationWarning`, the one category `filterwarnings` in `pyproject.toml`
turns into an error.

## Errors and diagnostics

- **Document problems** render as failure markers and are listed in `diagnostics`. `strict=True`
  raises `RenderRefused` instead, carrying the diagnostics.
- **Configuration problems** raise before rendering, with every problem named: an invalid style,
  setting, or locale raises `StyleError` (this includes a `{field}` that a text template does not
  accept or lacks, a `--set` value that is not valid YAML, and an `extends` cycle); an unknown output format, or a document that is not inside the configured document root, raises `OptionsError`. Both are
  `RenderError`s (and `ValueError`s, as they always were). Every renderer error pickles, so it
  survives `multiprocessing`.
- **Internal inconsistencies** raise `InternalError`, and the CLI exits with 70.

Diagnostics reuse `legaldown.Diagnostic`. The renderer adds rules only it can evaluate:
`ref-not-enumerated`, `path-not-relative` and `path-outside-root` (Errors for a file reference that is
not relative, or that leaves the document root, §2.3; reported here because validator 0.4 checks
neither), specification rule ids, plus renderer-specific ids prefixed `render-`:
`render-not-processed`, `render-link-refused` (a Warning for a link whose URL scheme links may not use; its text is shown), `render-locale-fallback` (an Info when no formatting locale is known, a Warning when a duration unit has no CLDR pattern in the locale and English is used), `render-ref-ambiguous`, `render-term-limit` (a Warning when defined terms refer to each other too deeply or too often: past 32 nested terms, 200,000 inline nodes resolved inside repeat computations of a term text (only cycles cause them), or 60 inline levels nested inside an open term, a `{{term:}}` shows its id; one block's own nesting, up to the builder's 100 levels, never counts), `render-designation-cycle` (a Warning for a heading that refers back to itself under the `none` scheme) and `render-designation-limit` (a Warning under the `none` scheme for headings that refer to each other past 32 headings, 60 nested levels, or 1,000 characters, and for a reference to a heading longer than 1,000 characters, which shows its first 1,000), and `render-term-too-long` (a Warning for a defined term whose text, with its references resolved, is longer than 1,000 characters: `{{term:}}` then shows the definition id), and the rules the DOCX planner reports on what Word draws differently from the other formats (`render-docx-section-label`, `-list-depth`, `-letter-overflow`, `-roman-overflow`, `-shared-counter`, `-number-mismatch`, `-reference`, `-reference-cycle`, as Warnings, `-alternative`, `-static-restart` and `-reference-word-only` as Infos; see "The DOCX planner"). The validator's
diagnostics carry their line (§16.9), and so do the renderer's own, and the CLI prints it as
`file:line:`.

**Lines.** The builder asks `Document.line_of` for the line of every section heading, top-level
block and list item (an item's pre-order number, which the builder already tracks for markers) and
stores it as `line` on `Section`, `Paragraph`, `ListItem`, `Table`, `Quote`, `DraftingNote` and
`CodeBlock` (not part of equality, so trees compare as before). A block inside a quote has the
quote's line; one inside a list item, the item's. The resolver tracks the line of what it is
resolving (`Resolver.line`, set with `_at`) and every renderer diagnostic carries it, so the
granularity is the block's (or the item's, or the heading's): a `{{ref:}}` or `{{term:}}` paragraph
is lifted by the validator and written back, so the renderer cannot place a directive within a
block without the validator's internal `Locator`, which would be a second bridge to its internals
(ADR 0007); it waits for
[validator#93](https://github.com/ForLegalAI/legaldown-validator/issues/93). A finding about
frontmatter is at its key (`diagnostics.key_line`, which wraps the public `source_map.key` and
returns None without a source map; one helper for every frontmatter reference). A term's text is
worked out at the term's definition (`Resolver.term_lines`, recorded by `_survey`) whichever
reference asks first. `Diagnostic.file` is `RenderOptions.filename`, which `render_file` and the CLI
set to the file name as the validator does (`Document.filename`, without the directory; `render` drops one given, `/` or `\`).

**Repeats.** `Resolver._warn` and `Resolver._reference` add a diagnostic through `diagnostics.record`,
which keeps one finding (rule, level, message) once, at the lowest line it was seen at: the
resolver works out the body before the title block, so a later sighting at a lower line moves the
reported one. `api.render` lists the renderer's diagnostics in the order of their lines (`diagnostics.by_line`,
none last) after the validator's, and leaves out those the validator's or the assembly's name already
(`diagnostics.repeats`). The renderer's `path-not-relative` and `path-outside-root` are left
out when the validator reported the same path at the same line, or at none (`diagnostics.covered_by`).

## Security

- Raw HTML in the source is never emitted (§8.7).
- Every text node and attribute is escaped.
- DOCX: every text, attribute, field instruction, bookmark name, relationship and property value goes
  through one sanitiser (`writers/docx/ooxml._t`, applied inside the element builders, so a caller
  cannot forget it). It drops what XML cannot carry (C0 controls but TAB, LF and CR, DEL, C1,
  U+FFFE/U+FFFF, lone surrogates): `xml.etree` alone writes `\x01` raw and a lone surrogate as a
  character reference, and Word then reports the file as unreadable. TAB and line breaks in a text
  become `w:tab` and `w:br`, never kept in `w:t`. A hyperlink relationship's Target is percent-encoded
  to a valid URI, or the link stays text. The part contents are fuzzed for well-formedness in
  `tests/test_docx_escaping.py`. The untrusted mode and the style caps apply to DOCX unchanged.
- A link is a hyperlink (§8.7) only if its URL is relative (no scheme, a fragment) or its scheme
  is one of `urls.LINK_SCHEMES`: `http`, `https`, `mailto`, `tel`, `ftp`, `ftps`, `sftp`, `sip`,
  `sips`, `sms`, `urn`, `geo`, `news`. It is an allow-list, because a renderer reads documents it
  did not write (principle 6 in concepts.md): protocol handlers (`ms-msdt:`, `ms-word:`,
  `search-ms:`, `vscode:`, `intent:`, `blob:`, `jar:`, ...) and pseudo-schemes (`C:\x`,
  `localhost:8080`) are not links, nor are `javascript:`, `file:`, `data:`. The scheme is read as
  a browser reads the URL (tabs, newlines, controls, and case are ignored). One predicate,
  `urls.is_link_target`, serves both writers and the resolver. A link that is not made renders as
  its text alone, in HTML and in text alike, and the resolver reports a non-empty one as the
  Warning `render-link-refused` (the writers emit no diagnostics, ADR 0003); an empty URL is
  text with no diagnostic. The builder turns off markdown-it-py's own `validateLink` (which would
  leave such links as literal Markdown) and keeps them as nodes, so that the resolver can report
  §2.3 paths and the allow-list is the one gate for every `href` and `src` the HTML writer emits
  (links, images, value links). A link with no text shows its URL as written (percent-encoding
  undone; the `href` stays encoded); the text writer leaves out ` <url>` when the URL, less a
  `mailto:` or `tel:` prefix, is the text.
- What the CLI prints on stderr never carries a raw control character from the document or the command
  line: every error line and every argparse error goes through `cli._safe` (`urls.printable` per line), so
  an input, answers, output or style name, a locale or a `--set` key echoed in one is escaped, and `cli._report`
  passes the file name and every diagnostic message (the renderer's and the validator's, which quote
  ids, paths and terms as written) through `urls.printable`, which writes every C0/C1 control, DEL,
  Unicode format character (bidi controls, zero-width), and U+2028/9 as `\xNN` or `\uNNNN`, so a
  crafted document cannot move the cursor, set a terminal title, or forge a line. The messages the
  API returns are not all escaped: only a path or URL quoted by the renderer's own rules
  (`path-not-relative`, `render-link-refused`) is, at its source; a caller that shows other
  messages must do the same.
- Every file reference (§2.3) must be relative with no URI scheme, and within the document root
  when one is configured, so a remote resource is never fetched or embedded and no path leads
  outside the tree the document belongs to. The references are `{{include:}}` paths,
  `attachments[].file`, `amends.file`, `supersedes.file` (the object form; a plain string
  describes the document and is no path), `translations` values, and image paths. Resolution, not a
  writer, enforces it (`Resolver._reference`, one place for every kind, over
  `urls.file_reference_problem`): an image whose path has a scheme (`https:`, `file:`, `data:`, a
  Windows drive such as `C:\x`) or starts with `/` or `\` (`//host`), or leaves the root, is replaced by
  its alt text; an `{{attach:}}` whose file fails is its text with no link; an include marker and
  an attachment placeholder's path stay as text. Each is reported as the Core Error
  `path-not-relative` or `path-outside-root`, which `--strict` refuses. An image with an empty path
  shows its alt text too, with no diagnostic (§2.3 has no rule for it). The checks are lexical,
  as §2.3 says: no `resolve()`, no symbolic link followed, no file read or tested for existence.
  The root is `RenderOptions.document_root` (`--root DIR`); with none, `../` is allowed, §2.3
  defining no default root (a service rendering documents it does not control SHOULD set one). A
  path's base is the document's directory relative to the root (`api._document_base`: the lexical
  `relpath` of the directory of `document_path` to the root, `/`-separated; the document at the
  root when it has no path, as text given to `render()` and standard input are); a document
  outside the root, or on another Windows drive, is an `OptionsError`, since the boundary would
  mean nothing. A backslash is read as a separator (the renderer's reading, so a path that goes up
  on Windows is not missed), `..` with trailing dots and spaces is `..` and `.` with trailing spaces is `.`, a control character (NUL included) makes the path `not-relative`, and percent-encoding is
  decoded once, only for what is used as a URL (an image's `src`, the link an `{{attach:}}`
  makes): `%2e%2e` is `..` there, and a directory name in a frontmatter or include path. The
  writers' image check is a second line. Markdown links are not file references (§8.7): they stay
  governed by the allow-list above, since the renderer reads nothing at their targets.
- At Rendering level, the only files read are the document, the style template, and the answers
  file the CLI reads with `--answers` (the Python API takes answers as a mapping). Attachment
  files and includes are never opened.
- **A style template is trusted input, unless it is loaded untrusted.** By default a template, a
  `--set` value and an `extends` path are the operator's, and the loader still keeps a value from
  breaking out of the stylesheet:
  - A value placed into the stylesheet (fonts, sizes, colours, margins, `page.size`,
    `html.max_width`) is refused with a `StyleError` naming the setting when it contains `/*`, `*/`,
    `</`, a backslash, a control character or a line break (`style/model.py:css_problem`, called
    from `style/loader.py:_convert` for every field declared with `css_field`). It is rejected,
    never stripped: removing one token can form another (`/` + `/**/` + `*` is `/*`). Anything else
    is the operator's, so `calc()` and `var()` load. A value is not validated as CSS, though, so
    `12pt (` is emitted as written and leaves the rest of the stylesheet unparsable.
  - `html.extra_css` is raw CSS, appended as written, but it may not contain `</style` in any case;
    `stylesheet()` also writes any `</` in it as `<\/` (the same inside a CSS string), for a `Style`
    built by hand.
  - `values.date` is a CLDR pattern handed to Babel, which raises on one it does not know, at every
    date in a document. The loader formats fixed dates with it (`_value_problems`), so a bad pattern is
    a `StyleError` naming the setting.
  - NUL and lone surrogates are refused in every value written into the stylesheet (`html.extra_css`
    too): no output encoding can write them.
  - `writers/html.py:_css` is the last line, for `writers.html.stylesheet()` given a `Style` built
    by hand, which the loader never saw: it strips `;{}<>\@`, control characters and line breaks,
    and removes comment delimiters until none is left. A lone `/` stays, since `calc(100% / 3)`
    needs it.
  - `extends` names any path the process can read, absolute or with `../`; only cycles are
    rejected. A style file is read with `yaml.safe_load`, as UTF-8.
- **Untrusted mode** (`load_style(..., trusted=False)`, `RenderOptions.untrusted`, `--untrusted`)
  is for a service that renders what its users send. The style is a built-in name, a `Style`, a
  mapping, or YAML text (a string with a line break), never a file path: nothing is read from disk
  but the package's own styles. `extends` may name only a built-in style. Each setting that reaches
  the stylesheet must match a strict grammar declared next to the field (`style/model.py:CSS_KINDS`:
  length, line-height, colour, font-weight, font-family, page size, margin, max-width), enforced in
  `_convert` for a mapping and, through `style_to_dict`, for a `Style` object and for settings
  objects given as overrides. The grammars allow no function, no variable and no `!important`, so
  `calc(1em + 2px)` and `var(--x)` are refused. `html.extra_css` must be empty. YAML text is at most
  64 KiB (UTF-8 bytes), may not use aliases (the "billion laughs" shape), and a number in it is at most
  32 characters (`_StyleLoader` reads `!!int`, `!!float`, `!!bool` and timestamps through guarded
  constructors, so a text PyYAML cannot convert is a `StyleError`, not its `ValueError`). Every
  free-text setting is at most 200 characters (a label or format is repeated wherever the output shows
  it, so an unbounded one multiplies the document's size) and `values.date` is one of the four names.
  A message lists 20 problems at most and "and N more"; an exception the loader did not foresee is
  reported as "the style could not be read", never with its own message. Every style, trusted or
  not, may nest 32 levels at most, in YAML text (refused by the scanner, `style/loader.py:_StyleLoader`,
  before anything is built, as PyYAML's cost is quadratic in the depth) and in a mapping. A message
  names the setting and the problem, and never quotes the style, a key, a template field or a path (a
  YAML error gives the line and column only), so it can be shown to the user who sent it.
  `--untrusted --print-style` loads the style this way and needs no root. `RenderOptions.untrusted`
  also requires a `document_root` (§2.3: a renderer for documents it does not control SHOULD set one): without it `render` raises an
  `OptionsError`, and the command exits 2. The option and the flag are one switch for both checks.
  Defaults are unchanged: trusted, no root required. A service should still choose the style
  itself. Document source has no power over the stylesheet either way: it is never emitted as HTML
  or CSS (§8.7).
