# Architecture

This page describes how the renderer is built. The decisions behind it are in
[decision records](decisions/). Read [Concepts](concepts.md) first for the vocabulary, and
[Styles and preferences](style-templates.md) for configuration.

---

## The pipeline

```
 source .lgd
      │  normalize_source(): strip BOM, unify line endings
      ▼
 ┌─────────────────────────┐
 │ 2. Assemble (answers)   │  only with an answers set: legaldown-validator's Template and Form
 └───────────┬─────────────┘  turn the template into its assembled document, which the rest renders
             ▼
 ┌─────────────────────────┐
 │ 1. Parse & validate     │  legaldown-validator: Document, ValidationResult (Core diagnostics;
 └───────────┬─────────────┘  its index: identifiers, markers, party/side/definition/attachment lookups)
             ▼
 ┌─────────────────────────┐
 │ 3. Build     build.py   │  source + validator → render tree (source inlines)
 └───────────┬─────────────┘
             ▼                style template (style/) ──┐
 ┌─────────────────────────┐                            │
 │ 4. Resolve   resolve/   │ ◄──────────────────────────┘  numbers, labels, anchors, display text,
 └───────────┬─────────────┘                               failure markers + Rendering diagnostics
             ▼
 ┌─────────────────────────┐
 │ 5. Write     writers/   │  html │ text   (docx, pdf later)
 └───────────┬─────────────┘
             ▼
 RenderResult(output, diagnostics, format, tree, style)
```

Stage 2, **assembly** with an answers set (§15.7), runs only when the job has answers, before
the document is parsed for rendering. A template rendered with answers is assembled first and the
assembled document rendered; without answers, it renders as its **template view** (§15.8).
Assembly is the core package's (`legaldown.parse_template(source).form(answers).assemble()`),
exact to the byte as §15.7.2 requires; the renderer only decides when to refuse:

- the template has Errors: §15.7.2 defines assembly only for a template without them
- the answers do (`answer-invalid`, `answer-missing`)
- the template needs other files (include fragments, LegalDown attachment files, translations),
  which the renderer does not read below the Full level (§17.6)

A refusal raises `RenderRefused` with the findings. Assembly Warnings, such as `answer-unknown`,
are reported with the rest. Blanks left unanswered stay, and render as blanks: the result is a
draft (§15.1), which `--final` reports.

`api.render()` runs the pipeline. Each stage returns frozen values. Only stage 4 reads the style's
semantic settings, and only stage 5 knows about file formats.

### 1. Parse and validate

`legaldown.parse` and `legaldown.validate` provide:

- the **metadata**: title, sides and parties, attachments, questions, language
- the **section identifiers** exactly as the validator resolved them: explicit `{#id}`, or
  generated by §5.3 with §5.5 collision handling. These come from `result.index.sections`,
  so the renderer can never compute a different anchor than the one the validator checked
- **lookups** for definitions, parties, sides, and attachments, already reduced to display names
  (§3.6)
- the **Core diagnostics**, each with a stable rule id

A document that cannot be read at all, such as one whose frontmatter is not valid YAML,
raises `DocumentError`. Every other problem renders.

### 3. Build the render tree (`build.py`)

There is one parser: the validator's ([ADR 0007](decisions/0007-one-parser-validator-model.md)).
The builder walks the validator's `Document` and turns each block into render-tree blocks. It
never decides a structural or LegalDown question itself:

| Question | Answered by |
|---|---|
| Sections, headings, identifiers | `Document.sections`, `result.index.sections` |
| Blocks: paragraphs, lists and items, quotes, tables, code, rules | `Document` blocks. List items hold blocks (nested lists, code, quotes, tables), a quote's content is the validator's `quote_blocks()`, and a code block's is `code_content()` |
| Where a marker (`{#id when=…}`) is placed, and what it means | `result.index.placed_markers`: each marker's block, field, offset, identifier, and condition |
| Whether the document is a template | `result.index.is_template` |
| Whether a quote is a drafting note, and its content | The validator's `is_drafting_note()` and `drafting_note_blocks()` |
| Which list item a marker belongs to | `PlacedMarker.item`: the item's number among the list's items, in pre-order |
| A lifted definition, `{{ref:}}` or `{{term:}}` block's source | The validator's `render_block()` |

These are all the validator's public API: the model and the result from `legaldown`, and, for
assembly, `parse_template` (`Template.form().assemble()`), `AssemblyError`, and the answers
reader `load_answers`, also from `legaldown`; the reading of source text from `legaldown.syntax`;
and the language's constants and rules from `legaldown.grammar`.

Within one block's text, **markdown-it-py parses inline Markdown only**: emphasis, links, code
spans, inline HTML. Directives are protected first by **sentinels**. Every directive, and every
`"Term" {{def:}}` span, is replaced with a private-use token, `\ue000<nonce>:<n>\ue001`, so
Markdown cannot reinterpret directive syntax, such as an underscore in an identifier. The nonce is
random for each build, so no text in a document, whether written literally, as an entity, or
percent-encoded, can pass for a sentinel. Emphasis that wraps only a defined term is dropped with
it, because the style decides how defined terms look (§7.2). A `{{def:}}` becomes a sentinel
that renders nothing. Every sentinel is wrapped in a punctuation character (U+2E31, Unicode
category Po, which markdown-it's `isPunctChar` accepts) on both sides, as the `{{` and `}}` it
replaces are punctuation, so that CommonMark's emphasis flanking rules see the same neighbours as
in the source: `_text_{{ref: a}}` closes its emphasis. A defined term in a link title or alt text shows its term but is not the
definition's anchor.

An HTML block in the model (`kind="html"`), a comment block included, renders nothing (§8.6). A
comment that starts a line is such a block, and it ends at the line holding `-->`, so text after
the `-->` on that line is dropped with it (CONFORMANCE.md, "Text after a comment").
Within a block's text, inline comments and tags are dropped; where one stood between two spaces,
one space stays, and before a line break none does. A list item whose blocks are all comments,
and a quote that holds only comments, are dropped (with a list left empty), after the whole list
is traversed so that the validator's item numbers stay aligned with the markers it placed. The
validator reports raw HTML other than comments (`raw-html`, §8.7). A heading
in a list item or a quote (`kind="heading"`) is not a section (§4.1) and shows as a bold line.

The builder never works around the validator's model. Where the model loses or misreads
something, the output follows the model, and the gap is listed in `CONFORMANCE.md` and filed on
the validator:
- link reference definitions (`[label]: url`) render as paragraphs

Guessing at lost structure was tried, and it traded each gap for new bugs.

### 4. Resolve (`resolve/`)

`Resolver.run()` works in three steps:

1. **Survey.** It finds which placeholder ids are used with conflicting types (§10.7). Which
   definitions exist (`result.index.definition_lookup`) and whether the document is a template
   (`result.index.is_template`) are the validator's, so there is nothing to collect for them.
2. **Structure.** Section numbers are the validator's own (`result.index.sections`), so a
   rendered number always matches the validator's: **alternatives** share a number (§15.8), and
   a skipped heading level counts as 1. The style only formats them, the n-th part of a number
   with the n-th level format. For paragraphs and list items, **alternatives** follow the
   validator's rule, applied the same way: an alternative directly follows its
   sibling, has the same identifier and a valid condition, and its full presence (its own condition
   and every enclosing one) excludes that of every unit already holding the number (§15.4, the
   validator's `exclusive()`). It then labels
   list items by depth and top-level paragraphs, and allocates output anchors. Every anchor
   target is registered with its **designation**: "4.2", "4.2(b)(ii)", or "Termination (a)"
   under the `none` scheme.
3. **Inlines.** It replaces every source inline with a resolved one:

| Directive | Resolves to | Failure markers |
|---|---|---|
| `{{ref:}}` | `CrossRef(designation, anchor)` (§13.3). A ref to an unnumbered item or paragraph falls back to its section's designation, with `ref-not-enumerated` | `[BROKEN REF: id]` |
| `{{term:}}` | `TermRef(label or the definition's rendered term text, def anchor)` (§7.3, §13.4); the text is the first definition's term resolved as at the definition, worked out on first use by `Resolver._term_text` (`_survey` only records which definition is first) | `[UNDEFINED: id]` |
| `"Term" {{def:}}` | `DefinedTerm` without quotation marks, anchored at `def:<id>` (§7.2) | n/a |
| `{{date:}}` `{{money:}}` `{{duration:}}` | `Value`, formatted for the locale by Babel (ADR 0005): amounts and durations keep every written digit (a fraction beyond Python's 4300-digit limit takes its plural form from its first 30 digits), and a duration without a pattern in the locale falls back to another length, the language alone, then English with `render-locale-fallback` | `[INVALID DATE: …]`, `[INVALID AMOUNT: …]`, `[UNKNOWN CURRENCY: …]`, `[INVALID DURATION: …]`, `[INVALID DURATION UNIT: …]` |
| `{{party:}}` `{{side:}}` | `Value(label or display name)` (§3.6) | `[INVALID PARTY: …]`, `[UNKNOWN PARTY: …]`, and the side forms |
| `{{field:}}` | `Value(raw value)` | `[INVALID FIELD: …]` |
| `{{placeholder:}}` | `Blank`, with the question's prompt if the style asks for it | `[INVALID PLACEHOLDER: …]`, `[UNKNOWN CURRENCY: …]`, `[INVALID DURATION UNIT: …]` |
| `{{attach:}}` | `Value(label or title)`, linked to the attachment placeholder or file (§6.4) | `[UNKNOWN ATTACHMENT: id]` |
| `{{choose:}}` | `Choice(all phrases)`, shown as `[a / b]` (§15.8) | `[INVALID CHOICE: q]` |
| `{{include:}}` | Not processed at this level (§17.5), with `render-not-processed` | `[NOT PROCESSED: include path]` |
| unknown name | Never printed verbatim (§11.5) | `[UNKNOWN DIRECTIVE: name]` |

A `label` never hides a failure marker (§11.5). Frontmatter strings go through the same resolver,
so placeholders in frontmatter render as blanks (§3.10).

The resolver also builds the **title block** (effective date, sides and parties; a party is named
there by `legal_name`, as an identification block, where `{{party:}}` in the text shows its
`label`, §3.6), **attachment
placeholders** (§13.8; files are not read at this level), and **signature blocks** (§2.2, always
with `legal_name`, per §3.6).

**Anchors.** Section, item, paragraph, and attachment anchors use their identifiers. Definition
anchors are `def:<id>`. Identifiers cannot contain `:`, so the two can never collide in HTML's
single id space (§5.6). When alternatives share an identifier, only the first keeps the anchor,
so ids stay unique. A definition's anchor is given out in one place, when its defined term is
resolved. Terms in titles or alt text get none. After everything is resolved, one pass drops the
link of any `{{term:}}` whose definition got no anchor, so term links always have a target.

Under the `none` scheme, a section's designation is its heading text, computed by a text-only
pass that gives out no anchors and leaves references out. Headings are numbered with their level
clamped to 1–5, as the validator numbers them.

### 5. Write (`writers/`)

> **A writer contains no LegalDown rules.** `tree.assert_resolved()` rejects a tree that still
> holds a source inline.

| Writer | Notes |
|---|---|
| `TextWriter` | Plain text (§13.6). A soft line break inside a paragraph is a space, a hard break a new line, and lists are indented with their labels, one quote stays one quote, and tables keep escaped cells and alignment. It takes the style's `attachments.separator` (default `page-break`; `rule` and `page-break` both print `---` before the attachments heading and between attachments). It is the **test oracle** for resolution |
| `HtmlWriter` | A self-contained HTML5 page, or with `standalone=False` just the `<article>`. Semantic markup, with labels as real text rather than CSS counters, and a stylesheet generated from the style's presentation settings, including print rules |
| DOCX, PDF | Planned ([ADR 0004](decisions/0004-html-first.md)) |

## Package layout

```
src/legaldown_render/
├── __init__.py        public API, __version__, SPEC_VERSION, CONFORMANCE_LEVEL
├── api.py             render(), render_file(), RenderOptions, RenderResult
├── cli.py             the legaldown-render command
├── errors.py          RenderError, StyleError, OptionsError, DocumentError, RenderRefused, InternalError
├── tree.py            render tree nodes (source and resolved inlines, blocks, document)
├── build.py           stage 3
├── resolve/
│   ├── resolver.py    stage 4
│   ├── numbering.py   counters, the §13.1 scheme presets, label templates
│   └── values.py      Babel formatting of dates, money, durations
├── style/
│   ├── model.py       the style dataclasses (every field has a default)
│   ├── loader.py      layering, extends, overrides, validation
│   ├── labels.py      built-in labels per language (en, cs, de, fr, pl, sk)
│   └── builtin/       default.yaml, continental.yaml, outline.yaml
└── writers/           html.py, text.py
```

## Dependencies

| Dependency | Why |
|---|---|
| `legaldown-validator>=0.4.0,<0.5` | The only LegalDown parser; Core validation |
| `markdown-it-py` | Inline Markdown inside one block's text (ADR 0007) |
| `babel` | CLDR locale data (ADR 0005) |
| `pyyaml` | Style templates |

All of them are pure Python. The DOCX and PDF writers will bring their dependencies in as extras.

The renderer uses only the validator's public API: `legaldown`, and the tooling modules
`legaldown.syntax` and `legaldown.grammar` (roadmap item U3, done in validator 0.4.0). Before 1.0
a minor release of the validator may change that API, so the dependency is pinned to one minor
version, and the tests fail on any of its deprecation warnings, since the next minor release
removes what is deprecated. The validator raises every one of them as a
`legaldown.LegaldownDeprecationWarning`, the one category `filterwarnings` in `pyproject.toml`
turns into an error.

## Errors and diagnostics

- **Document problems** render as failure markers and are listed in `diagnostics`. `strict=True`
  raises `RenderRefused` instead, carrying the diagnostics.
- **Configuration problems** raise before rendering, with every problem named: an invalid style,
  setting, or locale raises `StyleError` (this includes a `{field}` that a text template does not
  accept or lacks, a `--set` value that is not valid YAML, and an `extends` cycle); an unknown output format raises `OptionsError`. Both are
  `RenderError`s (and `ValueError`s, as they always were). Every renderer error pickles, so it
  survives `multiprocessing`.
- **Internal inconsistencies** raise `InternalError`, and the CLI exits with 70.

Diagnostics reuse `legaldown.Diagnostic`. The renderer adds rules only it can evaluate:
`ref-not-enumerated` and `path-not-relative` (an Error for an image path that is not relative, §2.3,
reported here because validator 0.4 does not check image paths), specification rule ids, plus renderer-specific ids prefixed `render-`:
`render-not-processed`, `render-link-refused` (a Warning for a link whose URL scheme links may not use; its text is shown), `render-locale-fallback` (an Info when no formatting locale is known, a Warning when a duration unit has no CLDR pattern in the locale and English is used), `render-ref-ambiguous`, `render-term-limit` (a Warning when defined terms refer to each other too deeply or too often: past 32 nested or 2,000 computed term texts a `{{term:}}` shows its id), and `render-term-too-long` (a Warning for a defined term whose text, with its references resolved, is longer than 1,000 characters: `{{term:}}` then shows the definition id). The validator's
diagnostics carry their line (§16.9), and the CLI prints it as `file:line:`. The renderer's own
have none yet: they are about a directive within a block, and the validator makes only a block's
line public (`Document.line_of`, U2).

## Security

- Raw HTML in the source is never emitted (§8.7).
- Every text node and attribute is escaped.
- A link is a hyperlink (§8.7) only if its URL is relative (no scheme, a fragment) or its scheme
  is one of `urls.LINK_SCHEMES`: `http`, `https`, `mailto`, `tel`, `ftp`, `ftps`, `sftp`, `sip`,
  `sips`, `sms`, `urn`, `geo`, `news`. It is an allow-list, because a renderer reads documents it
  did not write (principle 6 in concepts.md): protocol handlers (`ms-msdt:`, `ms-word:`,
  `search-ms:`, `vscode:`, `intent:`, `blob:`, `jar:`, ...) and pseudo-schemes (`C:\x`,
  `localhost:8080`) are not links, nor are `javascript:`, `file:`, `data:`. The scheme is read as
  a browser reads the URL (tabs, newlines, controls, and case are ignored). One predicate,
  `urls.is_link_target`, serves both writers and the resolver. A link that is not made renders as
  its text alone, in HTML and in text alike, and the resolver reports a non-empty one as the
  Warning `render-link-refused` (the writers emit no diagnostics, ADR 0003); an empty URL is
  text with no diagnostic. The builder turns off markdown-it-py's own `validateLink` (which would
  leave such links as literal Markdown) and keeps them as nodes, so that the resolver can report
  §2.3 paths and the allow-list is the one gate for every `href` and `src` the HTML writer emits
  (links, images, value links). A link with no text shows its URL as written (percent-encoding
  undone; the `href` stays encoded); the text writer leaves out ` <url>` when the URL, less a
  `mailto:` or `tel:` prefix, is the text.
- What the CLI prints on stderr never carries a raw control character from the document: `cli._report`
  passes the file name and every diagnostic message (the renderer's and the validator's, which quote
  ids, paths and terms as written) through `urls.printable`, which writes every C0/C1 control, DEL,
  Unicode format character (bidi controls, zero-width), and U+2028/9 as `\xNN` or `\uNNNN`, so a
  crafted document cannot move the cursor, set a terminal title, or forge a line. The messages the
  API returns are not all escaped: only a path or URL quoted by the renderer's own rules
  (`path-not-relative`, `render-link-refused`) is, at its source; a caller that shows other
  messages must do the same.
- An image path must be relative with no URI scheme (§2.3), so a remote resource is never fetched
  or embedded. Resolution, not a writer, enforces it: an image whose path has a scheme (`https:`,
  `file:`, `data:`, a Windows drive such as `C:\x`) or starts with `/` or `\` (`//host`) is
  replaced by its alt text and reported as the Core Error `path-not-relative`, which `--strict`
  refuses. An image with an empty path shows its alt text too, with no diagnostic (§2.3 has no
  rule for it). `../` stays allowed: §2.3 defines no default document root. The writers' image check
  is a second line.
- At Rendering level, the only files read are the document, the style template, and the answers
  file the CLI reads with `--answers` (the Python API takes answers as a mapping). Attachment
  files and includes are never opened.
- **A style template is trusted input.** Nothing in it is a security boundary:
  - A value placed into the stylesheet (fonts, sizes, colours, margins, `page.size`) is stripped
    of `;{}<>` only (`writers/html.py:_css`). That keeps it from ending its declaration or the
    `<style>` element, but not from breaking the CSS after it: `typography.font_size: "12pt ("`
    is emitted as written and leaves the rest of the stylesheet unparsable. It is not validated
    as CSS.
  - `html.extra_css` is appended to the stylesheet as it is, so it can contain anything,
    `</style>` included.
  - `extends` names any path the process can read, absolute or with `../`; only cycles are
    rejected. (A style file is read with `yaml.safe_load`, and as UTF-8.)
  A service that renders for several parties must choose the style itself, and never accept a
  style file, `--set` values, or `extends` paths from a user it does not trust. Document source
  has no such power: it is never emitted as HTML or CSS (§8.7).
